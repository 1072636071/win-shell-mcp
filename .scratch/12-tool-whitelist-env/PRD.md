# PRD / Spec — 工具子集白名单配置

Status: ready-for-agent
日期：2026-08-25
来源：PRD-07（`.scratch/07-token-optimization/PRD.md`）优化点 P1-2
优先级：P1
关联：ADR-0011（全量注册）、ADR-0010（双入口薄壳）、ADR-0007（兼容性红线）、**ADR-0016（四层优先级链——本工单取舍依据）**

## 问题陈述

不同部署场景只需要工具集的一个子集（纯只读巡检、git 流水线、文档处理……），但 MCP server 面当前除了全量暴露没有别的选项，未用到的工具仍然占用每次 `ListTools` 的固定开销。dsh 插件面已有 `config.exclude` 排除名单，MCP server 面缺少对称的裁剪手段。

## 解决方案

MCP server 面新增 `WIN_SHELL_TOOLS` 环境变量白名单（逗号分隔正名）：未列出的工具不注册，直接砍掉其固定开销。白名单解析为纯函数、fail-fast 报错；调用被裁掉工具时返回清晰错误，与拼错工具名的提示相区分。环境变量解析收敛在一个新建的配置模块中，作为本批优化唯一的新增代码 seam，供本工单与 11/15 号工单共用。

## 用户故事

1. 作为部署者，我想要用 `WIN_SHELL_TOOLS=git_status,git_add,git_commit,git_push` 这样的白名单启动 server，以便 git 流水线场景只暴露 4 个工具，固定开销近乎归零。
2. 作为部署者，我想要不设环境变量时行为与现状完全一致（全量 59 工具），以便默认零破坏。
3. 作为部署者，我想要白名单里写了不存在的工具名时 server 启动即失败并点名该条目，以便配置拼写错误不静默生效。
4. 作为部署者，我想要白名单按正名书写、别名自动跟随正名进退，以便裁剪语义简单可预测（写 `fs_list` 则 `ls`/`list_directory` 一起进退）。
5. 作为 AI，我想要调用一个被白名单裁掉的工具时收到明确提示"该工具未在当前部署暴露"，以便知道是部署裁剪而非自己拼错。
6. 作为 AI，我想要调用一个不存在的工具时收到与"被裁剪"不同的提示，以便区分两种原因。
7. 作为 AI，我想要在 `batch_run` 的步骤里引用被裁掉的工具时，该步失败并说明原因，而不是绕过白名单执行成功，以便白名单是真实边界。
8. 作为维护者，我想要白名单解析是纯函数（输入字符串、输出工具名集合或错误），以便不启动进程就能单测各种输入（空串、空格、重复项、未知名）。
9. 作为维护者，我想要环境变量读取只存在于一个配置模块，其余代码只消费解析结果，以便 env 读取不扩散成第二个事实源。
10. 作为维护者，我想要白名单与懒加载（11 号工单）的组合语义固定：先按白名单过滤，懒模式在过滤后集合上展示，以便叠加行为可预测。
11. 作为维护者，我想要该变量在 README 与 AI 速查表中有文档，以便部署者能发现它。

## 实现决策

1. **环境变量**：`WIN_SHELL_TOOLS`，逗号分隔工具**正名**，逐项 trim、忽略空段、重复项去重；未设置/空串 = 不过滤（全量）。别名不出现在白名单语法中，随正名共进退。
2. **配置模块（本批优化唯一新增代码 seam）**：新建一个纯函数模块承担环境变量解析，初版接口：工具白名单解析（输入原始字符串或 undefined，输出正名集合或"未知条目"错误）；11 号工单的 `WIN_SHELL_LAZY` 与 15 号工单的 `WIN_SHELL_TRUNCATE` 随后并入同一模块。模块内不直接读 `process.env`（读取留在唯一调用点），函数接受原始字符串入参，保证可注入测试。
3. **生效位置**：stdio 入口创建 server 时，用白名单过滤内置工具表后注入（工具表参数化注入的既有结构天然支持，无需全局态）。dsh 插件面**不**接入本变量——它已有 `config.exclude`，两套机制各管各面、语义对称即可。
4. **错误区分**：
   - 调用"存在于内置工具表但被白名单裁掉"的工具：失败消息明确含"未在当前部署暴露（WIN_SHELL_TOOLS）"。
   - 调用"内置工具表中不存在"的工具：维持现有 `Unknown tool: X` 语义。
   - `batch_run` 步骤解析同样受白名单约束：解析被裁工具时该步失败、错误文案同上，短路语义不变。
5. **fail-fast**：白名单含未知工具名时，启动阶段即抛错退出，错误信息列出全部非法条目；不做"忽略未知项"的宽容模式（静默忽略会让部署者误以为裁剪生效）。
6. **文档**：README 新增"环境变量"小节（本批优化共用，后续变量同节追加）；速查表（13 号工单）落地后同步一行。
7. **与懒加载组合**：白名单先过滤；11 号工单的域概览基于过滤后集合。

## 测试决策

1. **好测试的标准**：解析逻辑只测纯函数（表驱动：正常名单/空/空白/重复/未知项/含别名的非法项）；server 行为只测外部可观察面（`listTools()` 结果集、`callTool()` 错误文案），不测进程级启动失败路径（以纯函数的错误返回值等价覆盖）。
2. **seam**：配置模块纯函数（新模块，单测）；`createServer(filteredTools)`/`callTool(name, args, filteredTools)`（既有参数注入，无需新设施）。
3. **新增用例**：
   - 纯函数：白名单解析的各输入形态；未知条目错误含条目原文。
   - `createServer`：过滤后 `listTools()` 只含白名单工具；别名的正名被裁后别名同样不在列（别名本就不列出，断言行为不变）。
   - `callTool`：被裁工具 → "未在当前部署暴露"文案；不存在工具 → 原文案；白名单内工具（含经别名的调用，若 14 号工单已落地）正常。
   - `batch_run`：步骤引用被裁工具 → 该步失败、归因文案正确、短路。
4. **先例**：`tests/contract/errors.test.ts` 的纯函数表驱动模式；`tests/server.test.ts` 的工具子集注入（`createServer(baseline)`）。

## 超出范围

- 不做黑名单语法（排除语义已由"未列出"表达；dsh 面另有 `config.exclude`）。
- 不做按域白名单（`WIN_SHELL_TOOLS=domain:git` 之类的语法）——若 11 号工单落地后出现该需求再另立工单。
- 不做运行时热更新白名单（进程重启生效即可）。
- 不改 dsh 插件面行为。

## 补充说明

- 收益估算：按部署裁剪，极端场景（4-6 个工具）固定开销降 80%+。
- 风险：AI 请求未暴露工具会报错——以清晰文案兜底（用户故事 5/6）；这是白名单的应有行为，不是缺陷。
- **裁决依据（ADR-0016）**：本机制落实链第 4 项（输入 token 最少：更小工具面），以可能增加的第 1 项（轮速：AI 调用被裁工具报错→重试）为潜在成本——此取舍主体是**部署者**（部署者显式裁剪、认可此成本），属部署者侧的链内取舍，非设计缺陷。错误区分「被裁剪 vs Unknown tool」（链 1 保护：不因混淆多耗轮次）与 fail-fast 启动报错（防配置静默失效、避免 AI 多轮空转）均为「牺牲第 4 项多点错误文案、保第 1 项轮速」的链正确用法。
- 兼容性：纯新增开关、默认行为不变，不构成 ADR-0007 意义上的破坏。
- 预估工作量：2 小时（含配置模块骨架；该骨架是后续 11/15 的公共地基，宜优先落地）。
