# PRD / Spec — 常见 batch 预设文档

Status: ready-for-agent
日期：2026-08-25
来源：PRD-07（`.scratch/07-token-optimization/PRD.md`）优化点 P2-3
优先级：P2
关联：ADR-0015（batch_run；其中明确否决了 recipe 文件执行器）、ADR-0003（极简输出）、**ADR-0016（四层优先级链——本工单取舍依据）**

## 问题陈述

`batch_run` 要求 AI 每次从零编排步骤数组：选工具、排顺序、写引用模板、配断言。常见任务形态（读改写回、提交推送、批量采集）被反复编排，每次都花输出 token，还容易编错（引用路径写错、断言操作符用错）。ADR-0015 已否决"recipe 文件执行器"这类代码机制，但**文档形态**的预设模板不与该否决冲突——它只是把人类沉淀的编排经验放在 AI 可查阅的地方。

## 解决方案

在 `docs/batch-presets/` 下维护常见任务的 batch 编排模板：每个预设一个场景说明 + 可直接套用的 `batch_run` 入参 + 断言要点 + 适用与维护状态标注。`batch_run` 描述与速查表指向该目录。纯文档，零代码——比 recipe 执行器更轻，过时时也只过时文档本身。

## 用户故事

1. 作为要做"读文件→定位→替换→写回"的 AI，我想要一个现成预设可套用，以便不必每次重新编排四步与引用链。
2. 作为要提交推送代码的 AI，我想要 git 预设给出 `status→add→commit→push` 的每步断言写法，以便把"提交前无意外变更"这类校验前置到 server 侧。
3. 作为要批量采集文件内容的 AI，我想要预设演示 `fs_list` 结果经引用喂给后续读取的写法，以便掌握整串单引用保类型的用法。
4. 作为 AI，我想要每个预设标注适用场景与维护状态，以便判断它是否还匹配当前版本的行为。
5. 作为 AI，我想要预设里的语法与当前实现逐项一致（10 种断言操作符、`{{stepId.output.path}}` 模板、09 号工单后的默认极简输出），以便照抄不踩坑。
6. 作为维护者，我想要预设只是文档示例而非可执行代码路径，以便不违反 ADR-0015 对 recipe 执行器的否决。
7. 作为维护者，我想要预设数量克制（首批 4 个，只收真正高频的形态），以便该目录不沦为第二本说明书。
8. 作为维护者，我想要至少两个预设（不涉及写入外部状态的）在落地时经 `callTool("batch_run", …)` 实测通过，以便示例不是纸上谈兵。
9. 作为维护者，我想要 `batch_run` 的描述（10 号工单）与速查表（13 号工单）各有一处指针指向本目录，以便 AI 能发现预设。

## 实现决策

1. **目录与索引**：`docs/batch-presets/` 下每个预设一个文件 + 一个索引（索引含每预设一行：名称｜适用场景｜维护状态）。
2. **首批 4 个预设**：
   - 读改写回：`cat` 读取 → `grep`（`text_grep`）定位确认 → `text_replace` 替换（断言替换计数符合预期）→ 必要时复读校验；
   - git 提交推送：`git_status`（断言变更集符合预期）→ `git_add` → `git_commit` → `git_push`，每步断言要点给出；
   - 批量文件采集：`fs_list`（glob 过滤）→ 逐文件读取，演示整串单引用保类型的引用写法；
   - 环境自检：`system_disk` + `env_get` + `system_info` 的组合快照，断言磁盘余量等阈值（`gt` 操作符示范）。
3. **预设文件格式**：场景（何时用/何时不用）→ `batch_run` 入参 JSON（可直接粘进 `args`）→ 断言与引用的要点讲解（为什么这么断言）→ 适用版本与维护状态行。入参一律以 09 号工单落地后的默认形态为基准（不默认带 `verbose`）。
4. **语法基线核对清单**：断言操作符限 10 种枚举内；引用仅 `{{stepId.output.path}}` 形式；步骤失败短路的后果在"何时不用"中说明；步骤 `id` 显式命名（预设示例统一显式命名，便于引用可读）。
5. **指针接入**：10 号工单的 `batch_run` description 末句指向本目录；13 号工单速查表的 meta 节列一行。两处接入随对应工单落地，本工单提供被引用的落地物。**编辑协调**：10 号工单的 `batch_run` description 只改一次（与 08 合并编辑），"末句指向 `docs/batch-presets/`"必须含在那一次编辑内；本工单与 10 号实施时对齐此指针，避免 `batch_run` 描述二次编辑。
6. **维护约定**：`batch_run` 语法或相关工具输出变更的工单，须在同批检查本目录是否过时（写进各预设的维护状态行）；过时预设改状态标注而非悄悄留存。
7. **裁决依据（ADR-0016）**：预设文档落实链第 1 项（AI 不再每次从零编排、多步一轮完成）；「套用替代从零生成、省输出 token」为兑现后的连带收益（与 10 号 map 表述一致）。

## 测试决策

1. **好测试的标准**：文档本体不入测试（仓库无文档渲染管线），但"示例与实现一致"可以用一次性实测验证替代测试。
2. **实测验收**：落地时在临时目录对"读改写回"与"批量文件采集"两个预设经 `callTool("batch_run", …)` 实际跑通（含断言通过），结论记录于本工单评论区；"git 提交推送"与"环境自检"涉及外部状态，做静态核对（语法、操作符、字段名逐项对照实现），不实测。
3. **后续防线**：09 号工单的 `batch.test.ts` 已覆盖语法各面（断言/引用/短路），预设若照抄合法语法不会被实现侧悄悄破坏；文档侧的漂移由维护状态行与 6 号维护约定兜底。

## 超出范围

- 不做任何形式的预设执行机制（不接受"按名字调用预设"）——ADR-0015 的否决边界。
- 不做预设的参数化模板引擎（预设是示例，不是模板语言）。
- 不收低频场景（首版 4 个封顶，扩充需逐个论证频次）。
- 不做英文版。

## 补充说明

- 收益估算：AI 编排 batch 的输出 token 下降（套用替代从零生成），且断言写法有范本后编排错误率下降、减少失败重试的隐性开销。
- 风险：预设过时误导——以维护状态行 + 变更工单的连带检查缓解；预设过时的损害上限是"AI 照抄后收到明确报错"（断言/引用错误都有逐条归因），可控。
- 预估工作量：2 小时。
