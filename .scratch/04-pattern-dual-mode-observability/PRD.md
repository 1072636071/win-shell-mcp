# PRD: pattern 双模统一与误用可观测层

Status: ready-for-agent

来源：memorial 003-ai-tool-misunderstanding · ADR-0013 · 会谈定案 D1–D6

## 问题陈述

AI 调用方在使用 win-shell-mcp 的三个 pattern 类工具（text_grep、search_content、text_replace）时面临两类问题：

1. **语义不一致**：text_grep 与 search_content 是「字面量默认、斜杠包裹正则」双模，text_replace 却是纯正则——同名 pattern 参数在不同工具里含义不同，心智模型无法迁移；README 又把 text_grep 概括为「正则搜索文本」，进一步诱导调用方按正则习惯直接传 `a|b` 这类模式。
2. **误用不可见**：调用方传错形式后，工具按另一种模式静默处理——搜索得到 0 命中、无任何解释，AI 把空结果当事实继续推理，引发多轮无效排查甚至误判为工具 bug。现行判定还存在反向静默洞：想搜 `/tmp/` 这类恰好首尾斜杠的字面量会被误判为正则。此外 text_replace 默认全量替换且无命中数防护，替换范围出错时同样无声。

## 解决方案

三个工具统一为同一套「双模」语义：pattern 默认按所写字面量子串匹配（`.` `\` `*` 等一律原样，Windows 路径无需转义）；需要正则时用斜杠包裹（如把模式写成首尾各一个斜杠、尾部可选标志字母）。判定规则严格且永远向字面量收敛——任何不像合法正则写法的输入都按字面量处理，绝无第三种解释。

每次搜索/替换结果都明确告知 pattern 被按哪种模式解释了（新增模式标识字段），并在可疑误用发生时给出针对性提示（双向提示表）：该用正则没用、不该用时用了、路径反斜杠被转义吃掉等情形都会在一轮内被点破。text_replace 不再静默决定替换数量：0 命中报错并提示、1 命中自动替换并回显上下文供核验、多于 1 命中必须显式表态才执行。文档与工具描述同步改写，以「含反斜杠路径免转义」作为第一个示例直接建立正确预期。

## 用户故事

1. 作为 AI 调用方，我想让 pattern 默认按字面量子串匹配，以便搜索 `C:\Users\alice`、`foo.ts()` 这类文本时无需任何转义
2. 作为 AI 调用方，我想通过首尾斜杠包裹启用正则并在尾部附可选标志字母，以便需要时使用正则能力
3. 作为 AI 调用方，我想在正则模式下使用 i/m/s 标志（忽略大小写、多行锚点、单行点号），以便覆盖常见正则需求
4. 作为 AI 调用方，当我在 text_replace 用正则时想沿用 `$1`/`$&`/`$$` 回引用约定，以便与其他 JS 语境一致
5. 作为 AI 调用方，当我的字面量意图里本来就要匹配斜杠时，我想通过转义斜杠的正则写法表达，以便规则完全可预测
6. 作为 AI 调用方，当 pattern 含正则元字符却按字面量搜索得到 0 命中时，我想收到「像是正则但按字面量搜了」的提示，以便一轮内自纠
7. 作为 AI 调用方，当字面量搜索 0 命中时，我想收到拼写/大小写方向的通用提示，以便快速排查低级失误
8. 作为 AI 调用方，当命中数异常偏多且 pattern 形似正则时，我想收到「疑似被当作正则」的提示，以便发现 `/tmp/` 这类被误判为正则的字面量
9. 作为 AI 调用方，当我在正则模式下搜索反斜杠路径样式却 0 命中时，我想收到「反斜杠被当转义、请改字面量」的提示，以免拿着错误前提继续推理
10. 作为 AI 调用方，我想在每次结果中看到 pattern 被解释成的模式标识（字面量或正则），以便随时核对工具的理解与我的意图一致
11. 作为 AI 调用方，我希望 text_replace 与另外两个搜索工具语义完全一致，以便一次学会处处适用
12. 作为 AI 调用方，当 text_replace 的 pattern 是字面量时，我希望 replacement 也按纯字面插入（回引用记号原样保留），以便替换含特殊字符的文本不出意外
13. 作为 AI 调用方，当 text_replace 0 命中时，我想收到明确报错而非静默成功，以便立刻发现目标不存在或写错
14. 作为 AI 调用方，当 text_replace 恰好 1 命中时，我希望自动执行替换并返回命中处上下文片段，以便效率与核验兼得
15. 作为 AI 调用方，当 text_replace 多于 1 命中且我未显式表态范围时，我希望调用被拒绝并列出命中总数与各命中位置，以便由我决定全量还是限量
16. 作为 AI 调用方，当我可通过显式全量开关或次数上限表态时，我希望多命中的替换照常执行，以便批量操作仍然顺畅
17. 作为 AI 调用方，当结构像正则但标志字母非法时，我想收到列明合法标志的报错，以便立即修正而非困惑于空结果
18. 作为 AI 调用方，我希望 search_content 与 text_grep 对相同 pattern 的解释完全一致，以便跨文件与单文件检索无缝切换
19. 作为人类用户，我希望 README 与技能文档对三个工具的概括准确（默认字面量、斜杠启用正则），以便不被「正则搜索文本」式摘要误导
20. 作为 AI 调用方，我希望工具描述以「含反斜杠路径免转义」为第一示例并附正反例，以便填参当下就建立正确预期

## 实现决策

- 三个工具统一双模语义；text_replace 从纯正则改为双模属破坏性变更，在 0.x 发布前窗口实施，与 memorial 001 D8 清单同批（遵循 ADR-0007）
- 严格判定规则：整串解释为正则当且仅当——以斜杠开头且结尾、未转义斜杠恰好两个、内部斜杠必须转义书写、末段仅含本工具合法标志字母、正则体非空；任一条件不满足即整串按字面量处理（永远向字面量收敛）
- 标志白名单宁少勿多：两个搜索工具收 i/m/s；text_replace 另收 g 作为全量语义开关；不收扩展标志 x；搜索场景出现 g、或任何工具出现白名单外标志 → 报错并列出合法标志
- 已知残余洞接受并文档化：形如首尾斜杠各一个的两段字面量（如临时目录路径）仍会被判为正则——由「命中数异常偏多」提示兜底
- text_replace 的 pattern 与 replacement 语义联动：字面量 pattern 时 replacement 为纯字面插入、回引用记号不生效；正则 pattern 时沿用现有 JS 风格回引用实现（现状写死，零迁移）
- text_replace 新增可选布尔参数表示显式全量替换，与既有可选次数上限参数并存；命中数为 0 → 报错+提示；恰为 1 → 自动替换并回显上下文；大于 1 且两者皆未提供 → 报错并列出命中位置清单
- 搜索/替换成功响应新增模式标识字段（literal 或 regex）与可选提示字段；均为增量输出，符合输出契约与兼容红线
- ignoreCase 参数维持现状语义：对字面量与正则两种模式均生效
- 提示触发的阈值细节（元字符清单、「异常偏多」判据）为实现期调参项，方向由四行双向提示表锁定
- 工具描述文案重写：以反斜杠路径字面量免转义为首例，附字面量与正则的正反例对照及残余洞说明；README 工具表摘要同步修正；dsh 技能文档提及处复查
- 不引入独立的「正则开关布尔参数」（已论证否决，见 ADR-0013 替代方案）

## 测试决策

- 判定规则用表驱动测试：经工具接口传入各形态 pattern（多斜杠路径、两斜杠字面量、空体、合法/非法标志、转义斜杠体、纯元字符字面量等），断言匹配行为、模式标识字段值与错误码——外部行为断言，不测解析函数内部
- 提示表逐行验证：构造「元字符 0 命中」「普通 0 命中」「异常多命中」「正则模式反斜杠路径 0 命中」四类场景，断言提示文案出现与否
- text_replace 三分支全覆盖：0 命中报错、1 命中自动执行+上下文回显、多命中无表态报错+清单、全量开关与次数上限各分支；字面量模式下回引用记号原样插入的断言
- 一致性对照：同一组 pattern 在两个搜索工具上行为一致
- 编码边界沿用既有套件风格（GBK/UTF-8 自动检测下的搜索替换不回归）
- 先例：text 与 search 域的既有工具测试套件（describe 分组 + inputSchema 校验 + handler 行为断言的三段式）、集成冒烟沿用既有 MCP 客户端级测试
- 覆盖率遵循仓库既定阈值（行/函数/语句 ≥85%、分支 ≥84%）

## 超出范围
