# PRD / Spec — AI 工具速查文档

Status: ready-for-agent
日期：2026-08-25
来源：PRD-07（`.scratch/07-token-optimization/PRD.md`）优化点 P1-3
优先级：P1
关联：ADR-0001（命名策略：正名与别名）、ADR-0003（极简输出）、**ADR-0016（四层优先级链——本工单取舍依据）**

## 问题陈述

README 的工具清单是写给人看的：按域分组的表格、完整的自然语言说明、58 行的篇幅。AI 为了建立工具概览去读整个 README，要为安装说明、客户端配置、安全叙述等无关章节支付 token；而从 08 号工单开始，工具描述被刻意精简，被移出描述的使用细节（正则判定规则、编码细节、参数边界）需要一个稳定的承接处——目前这个承接处不存在。

## 解决方案

新建 `docs/ai-tool-cheatsheet.md`：一张极简速查表，每个工具一行（正名｜一句话用途｜关键参数｜别名），按 CONTEXT.md 的 15 命令域分组，另设 meta 工具与环境变量小节。AGENTS.md 与 CODEBUDDY.md（两者必须保持一致）加入指向速查表的引用，让 agent 加载时优先读它而非整个 README。用护栏测试把速查表的结构与 registry 对账，防漂移——仓库无 CI，漂移防线放在测试里。

## 用户故事

1. 作为 AI，我想要一份 59 行的速查表建立全部工具概览，以便获取工具全景的 token 比读 README 降 70%+。
2. 作为 AI，我想要每行含关键参数（含默认值与边界，如 `endByte` 0-based 含、`encoding` 默认 auto）与别名，以便不翻 schema 就能写出正确的首次调用。
3. 作为 AI，我想要被 08 号工单从描述中移出的使用细节（如 `text_grep` 的模式判定与反斜杠语义、`text_replace` 的双模约定）在速查表中有承接，以便精简描述不造成知识丢失。
4. 作为 AI，我想要速查表按 15 命令域分组并标注 meta 工具（`batch_run` 等），以便与懒加载模式（11 号工单）的域词汇对齐。
5. 作为 AI，我想要速查表含环境变量小节（`WIN_SHELL_TOOLS`/`WIN_SHELL_TRUNCATE`/`WIN_SHELL_LAZY`，随对应工单落地逐个补齐），以便知道部署侧开关。
6. 作为维护者，我想要护栏测试断言速查表与 registry 的结构一致性（正名全集、别名全集逐一对账），以便新增/改名工具时漂移立即变红。
7. 作为维护者，我想要一句话用途允许人工措辞（不与 description 逐字绑定），以便速查表与描述各自演化、只有结构强一致。
8. 作为维护者，我想要 AGENTS.md 与 CODEBUDDY.md 同步加入同一条引用，以便遵守两文件内容一致的仓库约定。
9. 作为维护者，我想要 README 工具清单补上 `batch_run` 一行（58→59）并链接速查表，以便两处清单都不再过期。
10. 作为维护者，我想要速查表顶部注明"面向 AI 的极简速查；人类向完整说明见 README"，以便读者各取所需、不互相迁就。

## 实现决策

1. **文件与结构**：`docs/ai-tool-cheatsheet.md`。顶部一段定位说明（面向谁、与 README 的分工）；主体为按 15 命令域分节的表格，列固定为四列：正名｜一句话用途｜关键参数｜别名；域内顺序与 registry 注册顺序一致；meta 工具（`batch_run`，及 11 号工单落地后的 `tool_groups`/`list_domain_tools`）单列一节；末尾环境变量小节（随 12/15/11 落地增补，初版可先列 `WIN_SHELL_TOOLS`）。
2. **内容来源**：一句话用途以精简后的 description 为底稿但允许更短更直白；关键参数只列高频/有坑字段（不是全量 schema 复述）；别名列全（含 14 号工单新增的短别名，两工单谁后落地谁补齐）。
3. **承接 08 的删除清单**：08 号工单从描述移出的使用细节，按工具归入速查表对应行的"关键参数/备注"——实施时以 08 评论区记录的删除清单交接。
4. **引用接入**：AGENTS.md 与 CODEBUDDY.md 同文追加一句引用（指向速查表，说明 agent 建立工具概览时优先读它）；两文件改动必须逐字一致。
5. **README 同步**：工具清单标题与表格补 `batch_run`（59 个），清单节开头加一行指向速查表的链接。
6. **不做生成器**：速查表人工维护、护栏测试对账（见测试决策）；自动代码生成文档的方案被否决——一句话用途需要人写，全量生成反而带来措辞噪音。

## 测试决策

1. **好测试的标准**：只断言结构一致性这类确定事实（正名集合、别名集合、行数），不锁一句话用途的措辞（人会演化措辞）。
2. **seam**：`builtinTools`（registry 的冻结快照）与文档文本本身——读文件、解析表格、对账，纯数据断言。
3. **新增护栏测试**：解析速查表的全部表格行，断言——正名集合 == registry 正名集合；每行的别名列 == 该工具的 `aliases`（无别名则为空标记）；域节标题集合 == 15 域（+ meta 节）；行数 == 工具数 + meta 数。模式沿用 `guard-mutating.test.ts` 的全集遍历护栏。
4. **AGENTS/CODEBUDDY 一致性**：沿用仓库既有约定即可（两文件当前一致是本工单的前提，改动时逐字同步）；是否追加一致性断言由实施者裁量，默认不加（避免测试面扩散）。
5. **先例**：`tests/tools/guard-mutating.test.ts`（全集护栏）；`tests/build.test.ts`（仓库级文件断言的先例）。

## 超出范围

- 不重构 README（只补 `batch_run` 行与一条链接，其余不动）。
- 不做英文版速查表（现生态以中文为主，翻译另立工单）。
- 不做速查表的自动生成脚本（已否决，见实现决策 6）。
- 不在速查表中写使用教程/示例编排（那是 16 号工单 batch 预设的领地）。

## 补充说明

- 收益估算：AI 获取工具概览的 token 降 70%+（59 行表格 vs 整个 README）。
- 维护成本：新增/改名工具需同步一行——护栏测试保证忘了会红，成本可控。
- 与其他工单的交接面：承接 08 的删除清单；收录 14 的新别名；登记 12/15/11 的环境变量；为 11 的域词汇提供人类可读镜像。建议本工单在这几个工单之间居中落地（08 之后、11 前后均可），交接项已各自写明。
- **裁决依据（ADR-0016）**：本机制落实链第 4 项（输入 token 最少：AI 读 59 行表而非整个 README）；其真实价值是**承接 08 精简掉的细节、避免 AI 首次调用写错而多走一轮（保链第 1 项）**——这是「廉价的第 4 项投入护住第 1 项」的链正确设计。
- **落地顺序约束（防时序空窗伤链 1）**：08 精简 description 与 13 填表间隔过长时，会出现「08 已删、13 未填」的窗口期，AI 丢失使用细节→首调写错→多走一轮。故 13 号工单宜与 08 相邻落地，或 08 的删除清单交接必须早于 13 填表完成；护栏测试共享单一计数来源（registry builtinTools 派生），避免 11-01（域数）与 13-02（行数）各自断言但口径漂移。
- 预估工作量：2 小时。
