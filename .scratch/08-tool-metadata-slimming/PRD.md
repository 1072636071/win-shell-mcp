# PRD / Spec — 精简工具描述与 inputSchema describe

Status: ready-for-agent
日期：2026-08-25
来源：PRD-07（`.scratch/07-token-optimization/PRD.md`）优化点 P0-1
优先级：P0
关联：ADR-0003（极简输出）、ADR-0015（batch_run）

## 问题陈述

每次 MCP 会话的 `ListTools` 都会全量返回 59 个工具的 `name + description + inputSchema + outputSchema + annotations`，这是无法规避的固定上下文开销（估算 4000-8000 token）。调查确认现状存在三类浪费：

1. 个别工具描述严重超长：`text_grep` 的 description 约 400+ 字符，完整写入了 literal/regex 判定规则、反斜杠语义、`/…/flags` 包裹写法与"已知残余洞"——这些是使用细节，不是选工具所需的信息；`batch_run` 的 description 约 200 字符。
2. 大量字段级 `.describe()` 重复字段名与类型已表达的信息（如 `path: z.string().describe('目录路径（绝对或相对）')`）。
3. 描述中存在事实错误：`batch_run` 的 description 曾声称"断言支持 9 种操作符"，实际枚举为 10 种（eq/neq/gt/gte/lt/lte/in/re/truthy/falsy）——**源码与文件头注释现已为 10 种，本工单确保 description 与之对齐**；多处注释与集成测试仍停留在 58 工具的旧值（实际 59，含 `batch_run`）。

## 解决方案

将每个工具的 description 压缩为"一句话用途 + 关键约束"，把使用细节留给 `docs/ai-tool-cheatsheet.md`（见 13 号工单）与 README；逐字段精简 `.describe()`，只保留字段名与类型表达不了的语义（单位、默认值、边界含开闭、陷阱）；逐工具校验精简后语义无损，并以预算护栏测试固定成果、防止回弹。

## 用户故事

1. 作为通过 MCP 调用 win-shell-mcp 的 AI，我想要 ListTools 的返回体量显著变小，以便每次会话的固定上下文开销降低 30% 以上。
2. 作为 AI，我想要工具描述只包含选工具所需的判别信息（做什么、≈哪个 Unix 命令、关键约束），以便不在实现细节上花 token。
3. 作为 AI，我想要易混工具对（`fs_read` vs `cat` vs `text_head`/`text_tail`、`find` vs `search_glob` vs `search_content`、`shell_exec` vs `run_command`）之间保留足够的判别语义，以便不误选工具。
4. 作为 AI，我想要 schema 字段描述只解释字段名说不出的东西（如 `endByte` 是 0-based 含、`auto` 编码的含义、断言 `path` 是点路径），以便参数一次填对。
5. 作为 AI，我想要 `text_grep` 的反斜杠/模式陷阱提示以精简形式保留，以便不因已知坑浪费一次失败调用。
6. 作为 AI，我想要 `batch_run` 描述中的操作符数量准确（10 种），以便不被错误文档误导。
7. 作为维护者，我想要一条 description 书写原则（"描述是给 AI 选工具用的，不是说明书"）落成可复述的规范，以便后续新工具保持同一风格。
8. 作为维护者，我想要一个元数据预算护栏测试，以便未来任何人的描述膨胀都会被测试拦下。
9. 作为维护者，我想要精简过程的语义无损逐工具校验有明确方法，以便验收不靠感觉。
10. 作为维护者，我想要顺手修正 58→59 的过期计数（集成测试期望值、`server.ts` 注释、README 口径），以便仓库内口径一致。

## 实现决策

1. **范围**：全部 59 个工具的 description 与 inputSchema 字段级 `.describe()`；outputSchema 中若有 describe 同样精简。不改任何工具的行为、参数名、输出形态。
2. **书写原则**：description = 一句话用途（含 ≈ Unix 类比，遵循 ADR-0001 命名策略的既有风格）+ 关键约束/默认值/陷阱。凡字段名 + 类型已能表达的 `.describe()` 一律删除或缩到一词。
3. **预算**：以精简前 `JSON.stringify(listTools())` 的总字符数为基线（实现时实测并记录在本工单评论区），精简后总量必须下降 ≥ 30%。单条 description 以 ≤ 150 字符为软上限，确需保留陷阱语义的（如 `text_grep`）可在护栏测试中显式声明例外清单。
4. **事实修正**：`batch_run` 描述中"9 种操作符"改为 10 种；`tests/integration/server.test.ts` 的 `EXPECTED_TOOL_COUNT` 由 58 改 59，`EXPECTED_TOOL_NAMES` 补入 `batch_run`；修正 `server.ts` 中"全部 58 个工具"的过期注释。
5. **语义无损校验方法**：逐工具对照精简前后文本，确认四个要素仍在（用途、关键参数语义、陷阱/边界、与易混工具的判别点）；易混工具对做一次集中判别评审。校验结论摘要追加到本工单评论区。
6. **与 10 号工单（batch_run 引导）合并实施**：`batch_run` 的 description 只改这一次，引导语与精简一次成型。
7. **细节外移承接**：被移出的使用细节不得丢失，由 13 号工单（AI 速查表）承接；本工单只做减法，不新建文档。

## 测试决策

1. **好测试的标准**：只断言外部可观察的元数据形态（经 `listTools()` 投影），不断言具体措辞全文（措辞会演化），不测实现细节。
2. **seam**：`src/server.ts` 的 `listTools()`（既有最高层 seam，参数注入、无全局态）。
3. **新增护栏测试**（元数据预算）：断言 `JSON.stringify(listTools())` 长度 ≤ 预算常量（= 基线 × 0.7，基线数值写入测试常量并注明测量日期）；断言每条 description 非空且 ≤ 软上限（例外清单显式声明）。模式沿用 `tests/tools/guard-mutating.test.ts` 的"全工具集遍历护栏"先例。
4. **修正既有断言**：集成测试工具数 58→59、名单补 `batch_run`。
5. **回归**：全量 `npm test` 必须保持绿——本工单不改行为，任何行为测试变红都说明改错了。

## 超出范围

- 不改变任何工具的输入/输出行为与字段。
- 不做懒加载（11 号工单）、白名单（12 号工单）、别名扩充（14 号工单）。
- 不新建速查表文档（13 号工单负责），本工单仅删减。
- 不引入 description 快照测试（维护负担大于收益，已否决）。

## 补充说明

- 风险与对策：描述过简导致 AI 误选工具是本工单唯一实质风险，对策是用户故事 3/5 的判别评审与用户故事 9 的逐工具校验；预算护栏只防膨胀，防不了过简，过简靠评审兜底。
- 依据 ADR-0007，当前处于 0.x 窗口，允许此类破坏性纠错；description 不属于兼容性承诺面，正式发布后亦可随版本演化。
- 预估工作量：半天。
- 依赖：13 号工单不必先落地，但被删细节应在 13 落地时补回速查表——两工单实施者需交接删除清单（记录于本工单评论区）。
