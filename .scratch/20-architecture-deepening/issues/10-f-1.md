# F-1 — git_checkout 一工具担三职：切分支/建分支/还原文件，参数组合矩阵复杂、输出形状动态

Status: ready-for-agent
强度：值得探索
域：git
工具：git_checkout
文件：src/tools/git.ts
来源：架构深化审查（jxx-improve-codebase-architecture，子 agent F）

## 问题

git_checkout 单工具承担三种职责：(1) 切换分支 branch；(2) 创建分支 branch+create=true；(3) 还原文件 paths（可选 branch 作还原源）。参数 branch/create/paths 的组合矩阵需 3 条互斥校验（create&&!branch、create&&paths、!branch&&!paths）把关，AI 调用前须理解组合规则。输出形状动态展开 { checkedOut, ...(hasBranch?{branch}:{}), ...(hasPaths?{paths}:{}) }，导致 2 处类型断言 as unknown as AnyToolResult，outputSchema 只能用 optional 字段近似描述，类型不精确。git 2.23+ 已引入 git switch / git restore 拆分 checkout 的多职责，win-shell-mcp 作为命令抽象层未对齐这一演进。

## 方案

方案A（对齐 git 演进）：拆为 git_switch（切/建分支，参数 branch/create）与 git_restore（还原文件，参数 paths/source），各输出形状固定 { switched, branch } / { restored, paths }，消除动态展开与类型断言。git_checkout 保留为别名委托 git_switch（兼容 AI 习惯）。方案B（保持单工具）：至少将输出形状固定为 { checkedOut, branch: string|undefined, paths: string[]|undefined }，消除动态展开。

## 收益

消除 3 条互斥校验与组合规则认知负担；输出形状固定，类型精确，消除 as unknown 断言；对齐 git 自身演进方向；每个工具单测更聚焦。代价：方案A 工具数 11→12，与工具数量最小化有张力，但 git_switch/git_restore 语义更清晰。

## 前后

**之前（浅）：**
git_checkout({ branch: feature })            // 切分支
git_checkout({ branch: feature, create: true })  // 建分支
git_checkout({ paths: [file.txt] })          // 还原文件
git_checkout({ branch: main, paths: [file.txt] })  // 从 main 还原
// 输出: { checkedOut: true, branch?: feature } 或 { checkedOut: true, paths?: [...] }
// outputSchema: { checkedOut, branch?: string, paths?: string[] }（形状不精确）
// handler 内 3 条互斥校验 + 动态展开 + as unknown as AnyToolResult

**之后（深）：**
git_switch({ branch: feature })               // 切分支
git_switch({ branch: feature, create: true })    // 建分支
git_restore({ paths: [file.txt] })               // 还原文件
git_restore({ source: main, paths: [file.txt] })  // 从 main 还原
// 输出: { switched: true, branch: feature } / { restored: true, paths: [...] }
// outputSchema: { switched, branch: string } / { restored, paths: string[] }（形状精确）
// 各 handler 无互斥校验、无动态展开、无类型断言
