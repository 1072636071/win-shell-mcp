# B-4 — fs_find 的 patternToRegExp 内联 escapeRegex 实现，未复用 utils/glob.ts

Status: ready-for-agent
强度：试探性
域：fs
工具：fs_find, find, search_glob
文件：src/tools/fs_find.ts, src/utils/glob.ts
来源：架构深化审查（jxx-improve-codebase-architecture，子 agent B）

## 问题

fs_find.ts 的 patternToRegExp（68-74 行）内联了正则元字符转义 `seg.replace(/[.+?^${}()|[\]\\]/g, "\\$&")`，这正是 utils/glob.ts 第 9-11 行已导出的 escapeRegex 的实现。两处转义逻辑重复，且 fs_find 的 patternToRegExp 仅支持 * 通配、大小写不敏感，而 utils/glob.ts 的 globToRegExp 支持 *、**、**/、?、[]、大小写敏感——fs_list 已用 globToRegExp，fs_find 未复用。局部性失败：若 escapeRegex 转义规则扩展（如处理新元字符），fs_find 内联版本不会跟着改，产生哑错误（某字符未转义导致正则语义漂移）。ADR-0013 pattern 双模约定未覆盖 fs_find（仅点名 text_grep/search_content/text_replace），fs_find 的 pattern 是 find -name 式文件名通配语义，不冲突。

## 方案

最小修复：patternToRegExp 内部复用 escapeRegex（import { escapeRegex } from '../utils/glob.js'），消除转义重复。更大修复（需 grill）：评估 fs_find pattern 改用 globToRegExp 统一通配语义，但会改变行为——大小写变敏感、多支持 ?/[]、** 路径通配，属破坏性变更（ADR-0007 兼容红线：0.x 前允许，1.0 后只加不改），需确认 fs_find 的「文件名模式」语义是否应与 fs_list 的 glob 对齐。

## 收益

转义规则单一事实源（escapeRegex）；fs_find 与 fs_list 通配语义有对齐路径（可选）。最小修复成本低、风险零；更大修复统一语义但需破坏性变更评估。

## 前后

**之前（浅）：**
fs_find.ts patternToRegExp 内联 `seg.replace(/[.+?^${}()|[\]\\]/g, "\\$&")`，与 utils/glob.ts escapeRegex 重复。

**之后（深）：**
patternToRegExp 复用 escapeRegex（最小修复）；或 fs_find pattern 改用 globToRegExp（更大修复，行为变更需 grill）。
