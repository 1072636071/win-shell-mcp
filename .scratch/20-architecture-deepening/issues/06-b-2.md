# B-2 — fs 破坏性操作未预留回收站保护接缝（ADR-0008/0009 已 Accepted 未实施）

Status: ready-for-agent
强度：值得探索
域：fs
工具：fs_rm, fs_cp, fs_mv, fs_write
文件：src/tools/fs_write.ts
来源：架构深化审查（jxx-improve-codebase-architecture，子 agent B）

## 问题

ADR-0008（回收站型保护）与 ADR-0009（默认关闭+环境变量+低价值名单+大小阈值）状态均为 Accepted 且 PRD ready-for-agent，但 fs 域四个破坏性 handler 当前直接调 Node fs API，无任何保护接缝：fs_rm 直接 fs.rm/fs.rmdir（223-292 行）、fs_cp 直接 fs.cp/fs.copyFile 覆盖（303-342 行）、fs_mv overwrite 时 fs.rm(dest) 再 rename（353-426 行）、fs_write append=false 时 fs.writeFile flag:'w' 覆盖（92-132 行）。未来实施 ADR-0008 时，需在四个 handler 散改：判断 WIN_SHELL_PROTECT 开启、命中低价值名单、超大小阈值、备份原数据到 backup/<操作ID>/、备份失败中止、写审计日志 operations.jsonl。这些逻辑在四处重复，且备份对象不同（fs_rm 备份被删目标、fs_cp/fs_mv/fs_write 备份被覆盖目标），覆盖语义不同（fs_cp 直接覆盖、fs_mv 先 rm 再 rename、fs_write flag:w 覆盖）。当前无接缝预留=接缝泄漏：破坏性操作的「保护」关注点跨四个 handler 泄漏。

## 方案

抽 src/protection/ 模块（首版可空实现），提供接缝 backupBefore(target, op, meta) 与 auditLog(meta)。各破坏性 handler 经接缝调 Node fs API：fs_rm → backupBefore(targetPath, () => fs.rm(...), { tool:'fs_rm', args })；fs_cp/fs_mv/fs_write 覆盖前 → backupBefore(dest, () => 实际覆盖, { tool, args })。首版 backupBefore 直接调 op（保护关闭），auditLog 空函数；未来 ADR-0008 实施时只改 protection 模块（加 WIN_SHELL_PROTECT 判断、低价值名单、大小阈值、备份、审计），handler 零改动。接缝形状需 grill：backupBefore 的 target 语义（被删 vs 被覆盖）、meta 结构、备份失败如何返回语义化错误。

## 收益

未来 ADR-0008 实施时只改 protection 模块一处，不散改四个 handler；备份/审计/低价值名单/大小阈值逻辑集中到深模块；handler 只保留域语义（预检查、返回字段）。删除检验：删除 protection 抽象，未来加保护时复杂性分散到四处（每处判断开启、备份、异常、审计），且易漏一处=哑错误（某工具未接保护，AI 误删无备份）——集中=深化信号，且防哑错误。

## 前后

**之前（浅）：**
fs_rm/fs_cp/fs_mv/fs_write 各自直接调 fs.rm/fs.cp/fs.rename/fs.writeFile，无保护接缝。未来 ADR-0008 实施需在四处散改备份+审计+名单+阈值逻辑。

**之后（深）：**
src/protection/ 提供 backupBefore(target, op, meta) + auditLog(meta) 接缝（首版空实现）；四个破坏性 handler 经接缝调 Node fs API。ADR-0008 实施时只改 protection 模块。
