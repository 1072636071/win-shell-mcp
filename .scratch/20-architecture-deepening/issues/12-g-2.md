# G-2 — batch.ts 843 行：引用解析子系统与断言引擎子系统纠缠于单文件，边界 case 难独立测

Status: ready-for-agent
强度：值得探索
域：archive / hash / json / meta
工具：batch_run
文件：src/tools/batch.ts
来源：架构深化审查（jxx-improve-codebase-architecture，子 agent G）

## 问题

batch.ts 单文件 843 行承载三套独立子系统：引用解析（getPath/lookupRef/resolveMixedString/resolveRef/resolveValue，~190 行）、断言引擎（runAssertion/runAsserts/compareNumeric + ASSERT_OPS，~140 行）、主循环（runBatchSteps 5 步串行短路，~130 行）。三套子系统当前均为 module-private，边界 case 只能经 handler 端到端测。但 handler 层 schema 校验会先拦截畸形输入：如引用解析的 {{}}、{{.}}、{{step..output}}、不闭合 }} 等被 batchStepInputSchema 的 z.record 放行后才能到达 resolveValue，而断言引擎的「未知操作符」switch default 分支被 z.enum(ASSERT_OPS) 永远拦截无法测；runAssertion 的类型边界（gt 对数组、re 对非字符串、in 对非数组）虽可经 handler 测但要构造完整步骤序列。引用解析与断言引擎经 stepOutputs Map 耦合，但耦合面极小（仅 runAsserts 调 resolveValue 解析 assert.value 中的引用）。删除检验：删除引用解析抽象，主循环需内联 ~190 行引用解析逻辑，复杂性集中到主循环、可读性下降——是深化信号。

## 方案

拆分为 batch/refs.ts（导出 resolveValue/getPath/lookupRef/REF_PATTERN/SINGLE_REF_REGEX 与 RefResult 类型）+ batch/asserts.ts（导出 runAssertion/runAsserts/ASSERT_OPS/AssertOp/AssertResult 类型）+ batch.ts（类型 BatchStep/StepResult + schema + runBatchSteps 主循环 + 工具定义）。refs 与 asserts 互不依赖；batch.ts import 两者。既有 createScopedBatchRunTool 不变。

## 收益

引用解析畸形输入（{{}}、不闭合、自引用前缀）与断言引擎类型边界（未知操作符 default 分支、gt 对非数值、re 对非字符串、in 对非数组）可独立单测，不必构造完整 batch 步骤序列绕过 schema；batch.ts 主循环从 843 行降至 ~510 行，串行短路 5 步流程可读性改善；refs 子系统可被未来 recipe/loop 等编排 meta 工具复用。纯重构、行为逐字节不变（0.x 纠错窗口内不触 ADR-0007 红线）。
