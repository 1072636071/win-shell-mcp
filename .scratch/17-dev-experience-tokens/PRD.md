# PRD / Spec — 开发体验优化（开发会话 token 降噪）

Status: ready-for-agent
日期：2026-08-25
来源：PRD-07（`.scratch/07-token-optimization/PRD.md`）优化点 P3-1
优先级：P3
关联：AGENTS.md 临时文件约定（`.temp/scripts/`）、ADR-0003（极简精神在开发流程的延伸）、**ADR-0016（四层优先级链——本工单的取舍依据）**

## 问题陈述

前九个工单优化的是"AI 使用工具"的 token，本工单优化的是"AI 开发本项目"的 token。调查确认三个浪费点：

1. 开发会话中反复手写一次性分析脚本（如"统计哪些工具描述超长""覆盖率短板在哪个文件"），同类脚本每次重写。
2. `npm test` 失败时 vitest 输出冗长，而覆盖率报告用 `text` 全表逐文件刷屏——AI 调试时要从大量噪音里找断言差异。
3. CHANGELOG 维护若基于完整 diff 回顾，每次发版都要把全部变更重新读一遍，而本仓库的 commit message 本就带主题与 ADR 交叉引用，信息密度足够。

## 解决方案

三件事：在 `.temp/scripts/` 沉淀首批常用分析脚本并注明复用方式；调整 vitest 的 reporter/覆盖率输出形态，让失败信息更聚焦；把"CHANGELOG 只从 git log 提炼、不读全量 diff"写成开发章节的明文约定。全部是轻量改动，不碰产品行为。

## 用户故事

1. 作为开发本项目的 AI，我想要 `.temp/scripts/` 里有现成的"元数据长度分析"脚本（输出各工具 description/schema 长度排行），以便做 08 号工单式的精简时直接复用，不必重写。
2. 作为 AI，我想要一个"测试覆盖率短板"脚本（从 coverage 数据列出未达标文件），以便定位补测方向时一步到位。
3. 作为 AI，我想要每个沉淀脚本头部注明用途与运行方式，以便复用时零猜测。
4. 作为调试失败用例的 AI，我想要 `npm test` 的输出聚焦在失败断言本身，以便少读无关噪音。
5. 作为 AI，我想要覆盖率摘要只出总表（每文件明细留在 html 报告），以便终端输出不被几十行逐文件表格淹没。
6. 作为维护者，我想要 reporter 调整经过一次真实失败场景的输出对比验证，以便"更精简"是实测结论而非感觉。
7. 作为发版维护者，我想要 CHANGELOG 条目从 `git log` 的 commit message 汇总提炼，以便发版回顾不必重读全部 diff。
8. 作为维护者，我想要该做法明文写在开发文档里，并以"commit message 须自带主题与 ADR/工单引用"为配套要求，以便提炼有据可依。
9. 作为维护者，我想要以上改动都不改变任何产品行为与测试结果，以便全量测试保持绿就是验收。

## 实现决策

1. **脚本沉淀**（遵循 AGENTS.md 的 `.temp/` 约定）：
   - 元数据长度分析：读 `listTools()` 投影，输出各工具 description 长度与 `JSON.stringify` 后 inputSchema/outputSchema 长度的降序排行——08 号工单与其后续复查的直接工具；
   - 覆盖率短板：解析 `coverage/` 的 v8 产物，列出低于门槛（lines 85 / branches 84，与 vitest 配置一致）的文件清单；
   - 每个脚本为独立可运行的 Node 脚本，头部注释写用途、运行方式、输出说明；脚本随写随沉淀，本工单只保证首批两个落地。
2. **vitest 输出降噪**（裁决依据 ADR-0016：落链第 3 项「输出 token 最少」，且不以损害链第 1/2 项「轮速/请求最少」为代价——门槛判定与关键失败信息不丢失）：
   - 覆盖率 reporter 由 `["text", "html"]` 改为 `["text-summary", "html"]`——终端只留总表，逐文件明细看 html（`coverage/index.html` 本就生成）；此为可观测性降级的取舍：逐文件明细从终端移到 html，`text-summary` 在阈值未达标时仍会列出不足文件与指标，故关键失败信息不丢失；
   - 测试本体 reporter：在 default 的失败输出基础上，实测对比内置精简型 reporter（以实施时 vitest 版本实际提供的选项为准）在真实失败场景下的输出量，选择"保留断言差异、去掉装饰"的一款并在配置中注释选择理由；若无更低噪且不失信息的选项，则保持 default 并在评论区记录结论——不为了改动而改动。
3. **CHANGELOG 约定**（裁决依据 ADR-0016：落链第 3 项「输出 token 最少」换取链 1/2 的省事——发版不再重读全量 diff）：在 README 开发章节增加一段流程约定——CHANGELOG 条目从 `git log`（自上个版本标签起，仓库尚无标签时以最近一次版本提交为基线）的 commit message 汇总、分类（Added/Changed/Fixed）、补 ADR 交叉引用；不要求回顾全量 diff；配套要求是 commit message 必须自带完整主题与引用（本仓库现有风格已满足，约定只是固化）。
4. **边界**：三项改动均不触碰 `src/`、不改测试断言、不改覆盖率门槛。

## 测试决策

1. **好测试的标准**：本工单改的是开发设施与流程，产品行为零变化——"全量 `npm test` 保持绿"就是最强验收；对新增脚本只做最小冒烟。
2. **seam 与用例**：
   - vitest 配置变更后全量跑一次 `npm test` 与 `npm run coverage`：全部通过、覆盖率数值与门槛判定不变；
   - 失败场景对比：人为制造一个失败用例，截图/记录变更前后输出行数与关键信息完整度，结论写入评论区（用户故事 6）；
   - 两个新脚本冒烟：在本仓库实际跑通、输出非空且格式正确（临时目录产物，不入仓库测试管线）。
3. **先例**：`tests/build.test.ts`（仓库级设施断言的先例）；本工单不新增入库测试文件——开发设施的验收以一次性实测记录代替，避免为"测试测试配置"引入维护负担。

## 超出范围

- 不引入 CI（仓库现状无 CI，漂移防线保持在本地测试）。
- 不做 CHANGELOG 自动生成脚本（约定先于工具；真出现重复劳动再另立工单）。
- 不沉淀首批两个之外的脚本（避免 `.temp/` 一次变成垃圾场，按需积累）。
- 不改覆盖率门槛与 include 范围。

## 补充说明

- 收益估算：开发会话的 token 消耗下降——脚本复用省去重写，失败输出降噪省去阅读，CHANGELOG 流程省去 diff 全读。三者均难精确计量，故列 P3。
- `.temp/` 语义提示：脚本放 `.temp/scripts/` 是遵循仓库约定（临时但可复用）；若某个脚本被证明长期高频使用，可在后续工单讨论是否升格入 `docs/` 或工具链，本工单不做。
- 预估工作量：半天。
