# 三模式提示词全文（英文生效版 + 中文阅读版）

> **中文对照只供人阅读，不进入任何运行时。** 生效文本只有英文那一份：
> `presets/wshell-*/agent.cordis.yml` 里 `persona` 行的 `text` 值。中文翻译不落地成
> 文件、不被 harness 读取，也不参与装配。改英文要同步改这里；只改中文一律无效。

装配规则（为什么这些句子就是模型看到的全部系统提示）见 [README.md](README.md)。

## WShell 标准模式

目录：58 win-shell 域工具 + DSH `tool-fs` 组（read / write / edit / read_image）
+ DSH `tool-web` 组（web_fetch / web_search）= **64 工具**。lsp 为可选能力，
本模式不纳入（commit b8c76c2）。

生效英文（86 字符）：

```text
You are a helpful software engineer assistant. Relative paths resolve against {{cwd}}.
```

中文对照（阅读用）：

```text
你是一名乐于助人的软件工程师助手。相对路径以 {{cwd}} 为基准解析。
```

设计意图：目录里 58 条工具描述本身足够说明各工具做什么，persona 不再挂工具映射表
或规则清单。唯一必须写进 persona 的是**相对路径基准**——它跨全部工具成立、且
schema 表达不了（工具参数只会写"默认工作目录"，不会告诉模型那个目录是哪个）。
缺了它，模型要么先花一轮调 `pwd`，要么按猜测落盘。

> 这句为真的前提是 `DSH_CWD` 与会话 cwd 同值；对不齐时改用 `pwd` 指向式写法，
> 见 README.md 的「`{{cwd}}` 成立的前提」条目。

## WShell 批量模式

目录：同标准模式，但放行 `batch_run` = **65 工具**（59 win-shell + 4 fs + 2 web）。
meta 导航工具 `tool_groups` / `list_domain_tools` 仍剔除。

生效英文（86 字符，**与标准模式逐字相同**）：

```text
You are a helpful software engineer assistant. Relative paths resolve against {{cwd}}.
```

中文对照（阅读用）：

```text
你是一名乐于助人的软件工程师助手。相对路径以 {{cwd}} 为基准解析。
```

设计意图：本模式的差异**只在目录**。「多步操作优先用 `batch_run` 一次完成，避免多轮
往返」这条引导住在 `batch_run` 自己的工具描述里（`src/tools/batch.ts`），理由是：

1. 该事实只关于"在多个工具里选哪个"，工具描述是它的天然归属地；
2. win-shell-mcp 有两种交付形态，MCP 形态根本没有 persona，只有描述能同时覆盖两边
  （`tests/tools/guard-metadata-budget.test.ts` 的工单 10 护栏也钉住了描述里的
   「优先」「一次」与读文件/替换/写回场景要素）；
3. persona 再写一遍就是同一事实两处表述，会随时间各自漂移。

`presets.test.ts` 断言两模式 persona 逐字相等，防止有人日后往批量 persona 里加规则。

## WShell 全量模式

目录：58 win-shell 域工具 + DSH 官方 `standard`（完整编码 agent）原生组合
（一次性 shell / fs / fs-search / jobs / skill / goal / plan-mode / subagent /
subagent_fork / workflow / ralph / ask-user / todo / web）。剔除 experimental/opt-in
包与生产未装 provider（工单 06 口径）。

生效英文（733 字符，`agent.cordis.yml` 里以 `text: >-` 折叠书写，装配后为单段）：

```text
You are a helpful software engineer assistant. Relative paths resolve against {{cwd}}. While plan mode is active, read and search only: no edits, no formatters or code generation that rewrites tracked files, no commits. Imperative requests mean plan the work, not do it; your own conversational agreement with the user approves nothing. Submit the finished decision-complete plan as markdown with a # title through exit_plan_mode, as the only and final tool call of that response; if a review rejects it, fold the feedback in and present again. Delegate with subagent in the background by default: start independent delegations together in one response and keep working meanwhile, and wait only when your next step needs that result.
```

中文对照（阅读用，按句对应）：

```text
你是一名乐于助人的软件工程师助手。相对路径以 {{cwd}} 为基准解析。

处于 plan 模式时只做读取与搜索：不编辑，不运行会重写受跟踪文件的格式化器或代码生成，
不提交。要求实现某事的祈使句意味着把活规划出来，而不是动手做；你与用户之间的对话式
一致意见（包括对你某个提问的确认回答）不构成任何批准。把成型的、决策自洽的计划以
markdown（以 # 标题开头）通过 exit_plan_mode 提交，并让它成为该次响应里唯一且最后的
工具调用；若评审驳回，把意见并入后再次提交。

默认以后台方式用 subagent 委派：在同一次响应里并行发起互不相关的委派，同时继续推进
手上有用的工作；只有当下一步确实依赖某个结果时才等待。
```

设计意图（这条最重要的取舍）：本模式保留 `complete: true`，而 `complete` 在 dsh 的
装配收尾会把**除 persona 以外的所有 section** 丢掉——包括本组合挂的 `plan:policy` 段，
以及 `tool-subagent` / `tool-workflow` / `tool-ralph` / `tool-jobs` / `tool-web` 等
原生插件自带的 guidance 段（合计约 2.2K 字符）。也就是说：**只要坚持极简目录，
这些官方说明书就一个字都到不了模型**。

因此本模式的 persona 必须自己承载两条"影响能不能安全做完"的规则，否则等于挂着
plan 模式却不知道 plan 模式不许改文件、挂着 subagent 却默认串行等待：

- plan 政策：不写会引发破坏性执行（在规划阶段改文件、把对话同意当批准）。
- 后台并行委派：不写会退化成串行等待，白白多轮次。

其余能力（workflow / ralph / goal / todo / skill / ask-user）交给 schema 自述，
不再往里堆规则——这是刻意的取舍边界，不是遗漏。

`plan-mode` 行仍带 `section` 配置：`@deepseek-ai/dsh-plan-mode` 的 Config 强制要求
非空 `section`，无法省略。该值在 `complete: true` 下**不参与渲染**，所以它与 persona
里的 plan 条款逐字同源（457 字符），由 `presets.test.ts` 的同源断言把守：哪天不再
`complete`，两处不会各自漂移。

## 若要去掉 `complete: true`

`complete` 是本目录一切取舍的前提。去掉它，标准/全量模式会重新拿回 harness 固定
opener 与上述原生 guidance 段（约 +2.2K 字符），全量 persona 里那两条就该删掉、交回
官方 section 承载；批量模式不受影响。届时请同步更新本文件与 README 的归属表。
