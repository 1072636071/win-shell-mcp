# ADR-0013: pattern 语义全线统一双模（字面量默认、/…/ 正则）与误用可观测层

状态：Accepted（memorial 内草案；结项时询问同步 docs/adr/）

日期：2026-08-24

来源：memorial 003-ai-tool-misunderstanding

## 上下文

- AI 调用方将 `a|b` 当正则传给 text_grep（实际按字面量处理），得到静默 0 匹配，误判为工具漏报并空烧数轮排查。
- 三个 pattern 类工具两种约定并存：text_grep/search_content 双模（src/tools/text.ts:76-103、src/tools/search.ts:249 对齐注释）vs text_replace 纯正则（text.ts:488）；README 摘要「正则搜索文本」（README.md:116）进一步误导。
- 既有 `/…/` 判定 `^\/(.*)\/([gimsuy]*)$` 存在静默洞：`/tmp/` 今天就会被解析为正则 `tmp`。
- 关键认知：对 AI 工具，「先验的载体是 description 而非 Unix 传统」——模型每次调用重读 description，偏离 grep 传统 ≈ 一行文案的成本；而 agent 检索「字面量高频 + 失败代价高」的特征更像编辑器系（VS Code/Sublime：字面量默认 + .* 开关）而非 CLI 系（grep/rg：正则优先 + -F 开关）。

## 决策

1. **全线双模**：text_grep、search_content、text_replace 统一为「默认按字面量子串匹配；`/…/` 包裹启用正则」。text_replace 由纯正则改为双模，且 pattern 与 replacement 语义联动：字面量 pattern → replacement 纯字面插入（`$1` 不触发组替换）；正则 pattern → JS 风格组替换 `$1/$&/$$`（现状写死，零迁移）。
2. **严格判定规则（永远向字面量收敛）**：整串解析为正则，当且仅当——以 `/` 首、尾包裹；未转义 `/` 恰好两个；体内 `/` 必须写作 `\/`；末段仅含合法 flags；正则体非空。任何一条不满足 → 整串按字面量。效果：`/usr/bin`、`/api/v1/`、`/a/b/` → 字面量（安全收敛）；`/foo/i`、`/d{3}/`、`/a\/b/` → 正则。flags 白名单宁少勿多：搜索 i/m/s；replace 另收 g（=全量替换语义开关）；不收 x。结构像正则但 flags 非法（如 `/foo/q`）→ EINVAL 报错——结构无歧义时意图明确，响错误优于哑回退。残余洞：形如 `/tmp/` 的恰好两斜杠字面量仍会被判为正则——接受并写入文档，由「命中异常多」hint 兜底（此时通常命中一大片，可见）。
3. **可观测层（双向 hint）**：搜索/替换结果新增 `patternMode: 'literal' | 'regex'` 字段；hint 按双向表触发：
   - 字面量、0 命中、含正则元字符（`\d [..] (..) + * ? ^ $ |` 等）→ 「像是正则但按字面量搜了，要正则请包 /…/」
   - 字面量、0 命中 → 通用提示（拼写/大小写，或 /…/i）
   - 命中数异常高、pattern 形似正则 → 「命中 N 处，疑似被当正则，检查是否想要字面量」
   - 正则模式、0 命中、pattern 呈反斜杠路径样 → 「\U 等被当作转义；搜路径请去掉 /…/ 用字面量」
   - replace 场景 0 命中 / >1 命中 → 同上两类 + 要求显式表态
4. **text_replace 安全语义（永不静默决定替换数量）**：0 命中 → 报错 + hint；1 命中 → 自动替换并返回命中处上下文片段供核验；>1 命中 → 未显式提供 `all:true` 或 `maxReplace:N` 时报错 EINVAL，返回命中总数与各命中位置清单。
5. **文案即防线**：description 以「`C:\Users\alice` 字面量免转义、反斜杠原样」为首例直接改写模型预期；README 摘要修正为「文本搜索（默认字面量，/正则/ 形式启用正则）」；docs/dsh/skills/jx-mode/SKILL.md 等提及处同步复查。
6. **时机（遵循 ADR-0007）**：text_replace 语义变更、flags 白名单等破坏性修改在 0.x 发布前窗口完成，与 memorial 001 D8 清单同批执行；具体排期归实施工单。1.0 后只加不改。

## 后果

- 正向：失误模式从「哑」（错配仍有结果、带着坏数据继续跑）变为「响」（0 命中/命中异常 + hint，一轮内自纠）；三工具心智模型一致；字面量高频场景（路径、代码片段、专有名词）零转义成本；`C:\Users` 类 Windows 路径可直接搜索替换，`\U` 不再被吃。
- 负向：与 grep/rg CLI 传统相反，人类用户需要适应「字面量默认」；text_replace 对既有调用方式是破坏性变更；判定规则与 hint 触发条件需要表驱动测试守护（用例清单见 memorial 003 待澄清·实施清单）；hint 存在误报可能，阈值需实现期调参。

## 替代方案

- **全线纯正则（grep/rg 式）**：忘转义产生静默错配（`foo.ts` 匹配到 `foopts`、`C:\Users` 的 `\U` 吃掉反斜杠），错误带输出、hint 无法触发，与本项目核心投资「可观测层」正面冲突。否决。
- **全线显式 regex 开关**：防不住「忘了设开关」（与忘了 /…/ 是同一失效路径），且引入 `/foo/i` × regex:false 组合语义负担。否决。
- **仅修文档不动行为**：描述写得再清楚，长会话中调用方仍会遗忘，静默失败依旧存在。否决为独立方案（文档修正保留为辅助手段）。
