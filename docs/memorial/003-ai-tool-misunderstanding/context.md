## 追问记录

### R1 · 2026-08-24 · 优化方向（第一问）

**事实（代码库自查）**：

- `text_grep` 的 pattern 约定：以 `/` 包裹为正则（支持 flags，如 `/foo/i`），否则按**字符串字面量**处理（`src/tools/text.ts:76-103` parseGrepPattern）。
- 工具 description："在文件中搜索匹配行。pattern 为字符串字面量或 /正则/ 形式。返回匹配行（含上下文）。"（`src/tools/text.ts:169`）
- README 工具表摘要写的是 **"正则搜索文本"**（`README.md:116`）——只提正则、未提默认字面量，与实际语义有偏差，是潜在的误导源。
- 返回结果含 `matches / count / truncated`，**不含 pattern 被按哪种模式解释的信息**——AI 无法从输出发现自己传错了形式，只能得到静默 0 匹配。
- `search_content`（跨文件）采用同一约定（`src/tools/search.ts:249`），`text_replace` 也是正则替换；ADR-0007 兼容红线：0.x 未发布但定位可发布开源产品，工具行为/结构变更需考虑下游 AI 客户端兼容。

**事故链还原**：README/直觉暗示"正则搜索" → AI 传 `a|b`（无 / 包裹）→ 工具按字面量静默处理 → 0 匹配 → AI 误判"漏报/工具 bug" → 多轮排查后自我纠错。

**提问**：这次优化要解决的核心问题是什么？

1. 消除"静默失败"【推荐】— 误解的代价不在传错参数，而在传错后工具静默返回 0 匹配、AI 把它当事实。约定不变（/正则/ 形式），返回结果增加 `patternMode` 字段；当按字面量处理、pattern 含正则元字符（如 `| ( ) * +`）且结果为 0 匹配时，附 hint："疑似想用正则，请用 /a|b/ 形式"。优点: AI 从输出即可自我纠错，一轮内止损；只加字段不改既有语义，向后兼容不触 ADR-0007 红线；改动小。缺点: hint 有误报可能（字面量本就含元字符的场景），需设计触发条件；不阻止误解发生，只缩短发现时间。
2. 改参数语义（显式 regex 参数）— 增加 `regex: boolean`，字面量/正则不再靠 / 包裹约定。优点: 根除歧义，最直白。缺点: 触碰 ADR-0007 兼容红线；/约定 在 text_grep、search_content、text_replace 多处联动，改动面大；新旧两种指定方式并存会造成两套真相。
3. 只改文档与描述 — README 摘要改为"文本搜索（默认字面量，/正则/ 形式启用正则）"，工具 description 加正反例（`"a|b"` 是字面量，`"/a|b/"` 才是正则）。优点: 零代码风险。缺点: 治标不治本——描述再清楚，长会话中 AI 仍会忘，静默失败依旧存在。
4. 不动 — AI 最终能自我纠错。优点: 零成本。缺点: 每次误解都烧一轮排查；README 摘要本身仍在误导后续使用者。

### R2 · 2026-08-24 · 用户质疑「方案 2 为啥不行」+ 根因再挖掘

**诚实修正**：R1 中「方案 2 触碰 ADR-0007 红线」的论据**错误，收回**。ADR-0007 原文（docs/adr/0007-compatibility-redline.md:23）明确：发布前（0.x）允许破坏性修改，且应主动借此窗口修正不合理设计。兼容性不是拦路虎，现在恰是改语义成本最低的窗口。

**方案 2 真正的问题（三条）**：
1. **防不住事故的实际发生路径**：事故根因是调用方没注意约定，不是约定有歧义。加 `regex:boolean`（默认 false）后，AI 照样裸传 `a|b` 不设 flag → 字面量 → 静默 0 匹配，坑一模一样。「记得设开关」的前提 = 「记得 /正则/ 形式」的前提，认知负担没降。防「忘了」只有两类手段：输出侧可见，或改默认语义（默认正则 → 漏报变静默误报，更危险）。
2. **两套真相的组合语义**：regex:false + `/a|b/`、regex:true + `/foo/i` 每个组合都要定义优先级与报错行为。
3. **联动面**：search_content 注释显式声明与 parseGrepPattern 对齐（src/tools/search.ts:270）；单改制造不一致，全改波及多工具 schema/测试/README/dsh 技能文档。

**公平记录**：方案 2 有一个真实优势——布尔开关在填参时比 prose 显眼；但本次事故发生时描述就写在 schema 里照样翻车，「填参时可见」不保险，「出错后可见」才是兜底。

**新发现的更深根因**：三个工具两种约定并存——text_replace 的 pattern 是**纯正则、无字面量模式**（text.ts:488「正则字符串（如 \d+）」，new RegExp(pattern,'g') 直接构造），text_grep/search_content 是双模。AI 从 text_replace 学到「pattern = 正则」的心智模型带到 text_grep，正是误解温床。

**R2 提问**：范围怎么定——只治静默失败，还是连约定不一致一起治？

**用户裁定（2026-08-24）**：**全部都治理好** —— 可观测性 + 文档修正 + 约定统一，一次做完。

### R3 · 2026-08-24 · 统一的目标形态是什么？（当前待决）

前提：无论选哪个方向，可观测性层（输出含 patternMode + 0 匹配 hint）和文档修正都要做，这里定的是「pattern 语义统一到哪」。

1. **全线双模（text_grep 式）【推荐】** — 所有 pattern 类工具统一为：默认字面量，`/…/` 包裹开正则（保留内联 flags 如 `/foo/i`）；text_replace 从纯真则改为双模。优点: 「搜字面量」（路径、代码片段、VietnamPlas 这类名词）零转义成本，是 AI 高频意图；失误模式是「忘开正则」→ count=0，可被 hint 精准兜住；`/…/` 是唯一能内联携带 flags 的形式；text_replace 顺带获得字面量替换能力（替换 `C:\Users` 不再需要手写 `C:\\Users`）。缺点: 与 grep/rg「正则优先」的 Unix 传统相反，逆着模型先验；text_replace 语义变更是破坏性修改（0.x 窗口内允许）。
2. **全线纯正则（grep/rg 传统）** — 默认正则，字面量需转义；text_replace 维持现状。优点: 顺应 Unix 传统与模型先验（AI 直觉「grep=正则」变成对的，本次事故某种意义上就是先验撞上了偏离传统的工具）；三工具中两个已如此或接近。缺点: 失误模式是「忘转义」→ 静默误报或错配（如 `foo.ts` 匹配到 `foopts`；Windows 路径 `C:\Users` 中 `\U` 被当身份转义吃掉反斜杠 → 静默匹配不上）——**有匹配时无法触发 hint**，可观测层兜不住这类错；字面量意图高频场景全要转义。
3. **全线显式开关** — 见 R2 分析：防不住「忘了设开关」，组合语义复杂，不再推荐，列出仅为完整。

核心权衡一句话：**字面量默认的失误看得见（count=0），正则默认的失误看不见（错配）**。

### R4 · 2026-08-24 · 方案 1 定案 + 判定规则发现矛盾

**用户结论（采纳）**：支持全线双模。论证补强：

- 「逆模型先验」这一缺点被高估：人靠肌肉记忆所以正则优先刻进手，模型每次调用都重读 description，**先验的载体是 description 而非 Unix 传统**；对人类偏离传统=高成本，对模型≈一行文案的成本。方案 2 唯一优点实际权重比 R3 所写更低。
- 先例分布：CLI 系（grep/rg）正则优先 + `-F/--fixed-strings` 开关；编辑器系（VS Code、Sublime）字面量默认 + `.*` 开关。agent 检索的失败代价与「字面量高频」特征更像编辑器系——我们是在给模型做编辑器式搜索，只是它长得像 grep。
- 必补边角：`/…/` 判定必须保守、可规格化，否则「字面量默认」自己漏出静默洞——搜 `/tmp/`、`/api/` 这类恰好首尾斜杠的字面量会被误判为正则，正是用来打方案 2 的那种哑错误。
- 配套规格（用户提供）：flags 宁少勿多（i/m/s；g 仅对 replace 有意义=全量替换；不收 x）；字面量模式 `.` `*` `(` `\` 等一律原样；text_replace 双模联动（字面量 pattern → replacement 纯字面、`$1` 不触发组替换；正则 pattern → 组替换，约定二选一写死）；replace 永不静默决定替换数量（0 命中报错+hint；1 命中替换并回显上下文；>1 命中未显式表态则报错并返回命中清单）；hint 做双向表 4 行（字面量 0 命中含元字符→提示 /…/；字面量 0 命中→拼写/大小写通用提示；命中异常多且形似正则→疑似被当正则；正则模式 0 命中含反斜杠路径样→`\U` 被转义、请去 /…/ 改字面量）；description 以 `C:\Users` 免转义为首例直接改写模型预期；残余洞（恰好两斜杠的字面量）接受+文档化，由「命中异常多」hint 兜底。
- 迁移：text_replace 破坏性变更就在 0.x 做，changelog + 反向 hint（第 4 行）兜过渡期老习惯。

**代码取证（本轮自查）**：

- 现行 parseGrepPattern 规则为 `^\/(.*)\/([gimsuy]*)$`（text.ts:84）——**`/tmp/` 今天就会被解析成正则 `tmp`**，该边角真实存在于当前代码，不是假设。
- 现行 flags 字符类含 gimsuy、无白名单校验；text_replace 回引用已是 **JS 风格 `$1/$&/$$`**（text.ts:497-506）；默认全量替换（hardcode `'g'`，text.ts:517），已有 `maxReplace` 上限参数（schema text.ts:491）。

**发现用户规格中的矛盾（待裁定）**：判定规则要求「未转义的 / 恰好两个」，但效果表声称 `/a/b/`（含三个未转义斜杠）→ 正则体 `a/b`。两者不能同时成立：

- 若严格执行「恰好两个未转义斜杠」：`/a/b/` → **字面量**。想写匹配 `a/b` 的正则须转义为 `/a\/b/`。此副作用良性：把 `/a/b/` 当字面量搜索恰好是多数输入者的本意（搜文本 "a/b"），错误方向仍是可见的 0 命中。
- 若只做结构贪婪匹配（首尾 `/` 取体）：`/api/v1/` 会被解析成正则 `api/v1`——重新打开这次要堵的静默洞，与其自己的效果表（`/api/v1/` → 字面量）冲突。

建议采用严格版，并把效果表中 `/a/b/` 一行修订为「→ 字面量（安全收敛，正则写法为 /a\/b/）」。

**R5 收口三项（最终规格确认）**：

1. 判定规则采用严格版——整串仅允许首、尾两个未转义 `/`，体内 `/` 必须 `\/`，否则整串按字面量。【推荐】
2. 结构像正则但 flags 非法（如 `/foo/q`）：EINVAL 报错 vs 退回字面量。推荐**报错**——结构已无歧义地表达了正则意图，flag 打错时哑回退会把 typo 变成令人困惑的 0 匹配；「向字面量收敛」原则只适用于结构歧义场景。
3. replace >1 命中的显式表态形态：推荐 count>1 时必须提供 `all:true` 或 `maxReplace:N` 之一，否则 EINVAL 并返回命中数+各命中位置；count==1 自动替换并回显上下文片段；count==0 报错+hint。replacement 回引用约定直接定案 JS 现状 `$1/$&/$$`，不再另问。

**用户裁定（2026-08-24）**：「可以」——三项全部按推荐收口（→ D6，ADR-0013 已起草）。

### R6 · 2026-08-24 · 新增两起「写删侧」事故 + 关键取证：ADR-0008 零实现

**用户报告的新事故（发生在 DSH 原生工具层，仓库 E:\work\sp\JxKnowledgeBase）**：

1. **write/edit 混用摧毁 CONTEXT.md**：AI 本想做定向 edit，实际调了 `write` 且参数是指纹错误的 edit 形参（old_string/new_string）——write 照常执行、整文件覆盖为错误内容；后续 edit 因 old_string 已不存在而报错才暴露。靠会话开头读过原文才得以恢复。
2. **根路径符断裂 × 递归删除 = 删掉整个 user 目录**。

**失败类别归因**：

- 事故 1 = 「错误参数仍成功执行」：schema 对未知参数宽容 + write 天然覆盖语义，指纹错误的调用不被拒绝。防护方向：①参数指纹纠错（dispatch 层通用检查：调用携带了本工具 schema 之外的知名参数 → EINVAL 并提示「你可能想调的是 X 工具」）；②先读后写强制（对已存在文件且本会话未 read 过 → 拒绝）；③备份兜底。
- 事故 2 = 「路径解析错位放大破坏半径」：递归删除 + 错根路径直奔家目录。防护方向：①危险目标守卫（盘根、家目录、浅深度路径的递归删除必须显式 confirm）；②删除前 realpath 规范化校验；③回收站兜底。

**关键取证**：**ADR-0008（回收站型破坏保护：backup/<操作ID>/ + fs_restore + fs_trash_list + operations.jsonl）状态 Accepted（2026-08-20，源自 memorial 002-destructive-op-log-recovery），但代码零实现**——src 下 grep `recycle|回收站|trash|fs_restore|fs_trash_list|operations\.jsonl|backup` 全部零命中，也无对应工具文件。事故 2 的解药已开好、未抓药。

**分层现实**：事故 1 的 write/edit 是 DSH 原生工具（deepseek-harness 仓库，本地有 checkout，可改但属另一项目）；win-shell-mcp 只能治理自己的 fs_write/fs_rm/run_command 等；用户侧最普适的恢复网是 git 化 + 及时 commit。

**哲学同源**：003 治「读侧误解」（pattern 双模 + hint），本次是「写删侧误解」——同一原则：把哑错误变响错误，把静默破坏变可恢复。

## 决策汇总

- **D1（2026-08-24）· 治理范围 = 全部**：可观测性（patternMode + 双向 hint 表）+ 文档修正（README「正则搜索文本」等）+ 三工具 pattern 约定统一，一次做完。用户拍板。
- **D2（2026-08-24）· pattern 语义全线统一为双模**：默认字面量、`/…/` 包裹开正则（内联 flags i/m/s）；text_replace 从纯正则改双模。理由：响错误（0 命中/命中异常，hint 接得住）vs 哑错误（错配还带结果继续跑）——可观测投资只对响错误有效；先验载体是 description 非 Unix 传统；编辑器系先例更贴 agent 场景。替代方案（全线纯正则、全线显式开关）被否决，见 R3/R4。用户拍板。
- **D3（2026-08-24）· 可观测与文案规格**：双向 hint 表（4 行，含正则模式反斜杠路径反向提示）；description 以 `C:\Users` 字面量免转义为首例；`/tmp/` 类残余洞接受并文档化。用户拍板。
- **D4（2026-08-24）· text_replace 安全语义**：永不静默决定替换数量（0 报错+hint / 1 替换+上下文 / >1 显式表态）；pattern 与 replacement 语义联动（字面量 pattern → replacement 纯字面）；回引用定案 JS 风格 `$1/$&/$$`（现状零迁移）。用户拍板；参数具体形态待 R5 第 3 项收口。
- **D5（2026-08-24）· 范围载体分流**：003 保持读侧议题纯粹、按 R5 尽快收口；两起写删侧事故（write 误覆盖 / 递归删除灾难）另开 **memorial 004-destructive-misuse-protection** 承接，范围候选 = ADR-0008 落地 + 危险目标守卫 + 参数指纹纠错，win-shell-mcp 层先行、DSH 原生层另行出工单。用户拍板（选方案 1）。
- **D6（2026-08-24）· R5 三项规格收口**：① `/…/` 判定严格版（整串仅允许首尾两个未转义 `/`，体内必须 `\/`，任一不满足→整串字面量；`/a/b/` 归字面量）；② 结构似正则但 flags 非法 → EINVAL 报错（响错误优先于哑回退）；③ replace >1 命中须显式 `all:true` 或 `maxReplace:N`，count==1 自动替换并回显上下文，count==0 报错+hint；④ 回引用定案 JS 风格 `$1/$&/$$`。用户拍板。
