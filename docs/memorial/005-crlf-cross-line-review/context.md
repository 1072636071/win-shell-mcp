# Memorial 005-crlf-cross-line-review

状态：进行中

## 诉求

（用户原话）

> \r? 转义在该引擎下第三次失败——win-shell 的 text_replace 对跨行模式确实无能为力，
> 按回退规则改用内置 pwsh（注明原因：跨行字面替换需要完整正则/字面量能力），
> 用字面量 .Replace() 精确修复并顺带把那个孤立 LF 归位为 CRLF。

衍生子目标：
1. 确认「text_replace 对跨行模式确实无能为力」这一前提是否为真。
2. 若为真，确认 pwsh 回退与字面量 `.Replace()` 方案是否最优；若为假，给出 win-shell
   原生修正路径，避免不必要的越权回退。

## 追问记录

**2026-08-24 · 事实核查（查代码库，stage-1 证据）**：

- `text_replace` 的正则路径在**全文**上跑 `/.../` 的 `exec()` 扫描
  （src/tools/text.ts · findAllMatches 553-575），并非逐行。即**跨行匹配在正则模式下天然支持**，
  显式 `\r?\n`、`s` 标志（`.` 匹配换行）、零宽锚点 `m` 均可用。
- 默认**字面量模式**用 `content.indexOf(value)`（text.ts 558-562），`\r` 被当作**字面反斜杠+r**，
  绝不匹配真实的 CR 字符。因此裸写 `\r?`（不包 `/`）→ 在 GBK/UTF-8 文件里搜不到真实 CRLF，
  = 0 命中 → EINVAL + hint。这是**模式误用**，不是引擎无能为力。
