# ADR-0008: 破坏操作保护——回收站型而非完整 undo

状态：Accepted

日期：2026-08-20

来源：memorial 002-destructive-op-log-recovery（D1/D4/D8/D10/D13/D14）

## 上下文

项目定位「无沙箱全权限、与裸 shell 等价」（ADR-0002），破坏性操作（fs_rm、fs_write 覆盖、fs_mv 覆盖等）直接生效、无日志、无备份、无撤销。AI 误操作（误删文件、覆盖源码）无任何挽回手段。用户诉求：所有破坏性操作记录日志、默认 `D:\log`、可配置、保证可恢复。

候选方案：

- **审计日志型**：只记录操作详情，不保存数据。恢复靠人工，被覆盖/删除的数据无法找回。
- **回收站型**：破坏前把原数据移入备份区（`<日志根>/backup/<操作ID>/`，含 meta.json），提供 `fs_restore`/`fs_trash_list` 还原；删除/覆盖均自动还原。
- **完整 undo 链**：每个操作生成逆操作记录，可回滚到任意历史点。

## 决策

**采用回收站型**：

- 破坏前将原数据备份到 `backup/<操作ID>/`（时间戳批目录，meta.json 记录原路径/操作/时间/工具参数/操作 ID）。
- 新增 `fs_restore`（按操作 ID 还原整批，原位置冲突则报错）与 `fs_trash_list`（列批次）。
- 备份失败即中止破坏操作，返回 AI 可理解的语义化错误（原因 + 可行出路）。
- 回收站不自动清理（无 TTL/容量淘汰），由用户自行管理。
- 审计流 `logs/operations.jsonl` 每破坏操作一行，与批次 meta.json 互补。

## 后果

- 正向：AI 误删/误覆盖可自助还原，兑现「所有破坏性操作都可以恢复」；批次自包含可整体移动/删除；错误契约面向 AI 消费。
- 负向：破坏操作变慢（先备份后破坏，大目标成本高——见 ADR-0009 例外规则）；备份区磁盘占用只增不减；回收站型无法回滚「操作序列」本身，只能逐批还原。

## 替代方案

- 审计日志型：无法真正恢复数据，诉求核心「可以恢复」落空。
- 完整 undo 链：跨盘 rename、权限、并发、部分失败场景复杂度不可控，与 MCP 一次一调用模型不匹配，且对 AI 调用方价值增量小。
